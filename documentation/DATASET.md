# Dataset Documentation

This project uses a COCO-style object-detection dataset that was filtered down to the five classes relevant to the application:

- person
- car
- motorcycle
- bus
- truck

The dataset is then converted into a YOLO-compatible training format with `images/` and `labels/` folders and a `data.yaml` configuration file.

## 1. Source

The original dataset source is the COCO 2017 object detection dataset from the official project page:

- https://cocodataset.org/

The project does not use all of COCO. Instead, it filters the dataset to only the relevant classes needed for the current task.

## 4. Dataset size

The prepared local YOLO dataset in this repository currently contains:

- Train: 23 images
- Validation: 2 images
- Test: 2 images
- Total: 27 images

This is a small project dataset and should be treated as a prototype dataset rather than a large-scale benchmark dataset.

## 5. Train/validation/test split

The project uses a deterministic split for the filtered dataset:

- Train: 80%
- Validation: 10%
- Test: 10%

The configuration is stored in the dataset metadata and generated by the preparation scripts. The resulting YOLO structure is:

```text
dataset/
├── images/
│   ├── train/
│   ├── val/
│   └── test/
├── labels/
│   ├── train/
│   ├── val/
│   └── test/
├── data.yaml
└── README.md
```

The project uses the same held-out split for reliable baseline and fine-tuned model comparison.

## 6. Preparation

The preparation process follows these steps:

1. Load the COCO annotation data.
2. Keep only the target classes.
3. Filter out images and boxes that are not relevant.
4. Convert bounding boxes from COCO format to YOLO format.
5. Split the filtered data into train, validation, and test sets.
6. Validate that each image has a matching label file and valid boxes.
7. Save the final dataset in YOLO format.

The relevant dataset preparation script is:

- `scripts/prepare_coco_dataset.py`

The validation script is:

- `scripts/validate_dataset.py`

## 7. Limitations

This dataset has several important limitations:

- It is small compared with production object-detection datasets.
- Some classes are absent or underrepresented in the held-out split.
- The project dataset is not a full CCTV dataset and does not capture all real-world deployment conditions.
- Distant objects, occluded objects, and crowded scenes remain difficult.
- A small training set increases the risk of overfitting and unstable evaluation results.

## 8. Beginner guide

Think of a dataset as a set of teaching examples for the model.

Each image in the training set is a lesson. Each label tells the model:

- what object is in the image
- which class it belongs to
- where the object appears

The model learns by seeing many examples of the same object type from different angles, backgrounds, and scales. A good dataset helps the model learn patterns instead of memorizing a few exact scenes.

## 9. Project-specific note

The dataset is intentionally narrow and practical for this project: it is optimized for the project classes and for creating a working prototype detection model, not for general-purpose large-scale deployment.

A good dataset for object detection contains many examples like:

- people walking
- cars on roads
- motorcycles in traffic
- buses in public spaces
- trucks in different scenes

It also helps if the images are different from each other:

- some are bright
- some are dark
- some are crowded
- some are open spaces
- some show objects close to the camera
- some show them far away

This variety helps the model learn better because it sees patterns in real situations, not just one narrow type of image.

COCO is useful because it provides this variety and includes our target classes.

## Stage 3: dataset preparation plan

For this project, the final dataset will contain only these five classes:

- person
- car
- motorcycle
- bus
- truck

We will use a YOLO-compatible layout:

```text
dataset/
├── images/
│   ├── train/
│   ├── val/
│   └── test/
├── labels/
│   ├── train/
│   ├── val/
│   └── test/
├── data.yaml
└── README.md
```

The project uses a deterministic split of approximately 80/10/10:

- train: 80%
- validation: 10%
- test: 10%

This keeps the test set independent from the training process and helps reduce data leakage.

The class mapping will be explicit and fixed as:

- 0 = person
- 1 = car
- 2 = motorcycle
- 3 = bus
- 4 = truck

Any classes not in this list will be excluded before training begins.

We will validate the dataset for:

- missing images
- missing labels
- invalid annotation boxes
- invalid class IDs
- unexpected classes
- duplicate filenames
- empty label files
- class imbalance

The dataset summary will report image counts and class counts before training starts.
